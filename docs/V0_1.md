# Runetime v0.1 — вертикальный срез

## Определение готовности

> Игрок пишет заклинание текстом на языке из `SPEC.md`, оно компилируется
> в байткод, исполняется стековой VM с лимитом топлива, попадает во врага
> на 2D-арене — а при обращении к освобождённой памяти убивает самого игрока,
> и трассировка объясняет, почему.

Срез закрыт, когда оба сценария проходятся вручную от начала до конца.

## Сценарий A — заклинание работает

1. Игрок открывает гримуар, видит текстовое поле и пример заклинания.
2. Пишет корректный `Fireball`, жмёт «собрать».
3. Компилятор сообщает успех, показывает стоимость в топливе.
4. На арене игрок кастует заклинание в сторону врага.
5. VM исполняет байткод, снаряд летит, враг получает урон и умирает.
6. В журнале видны потраченное топливо и число исполненных инструкций.

## Сценарий B — заклинание убивает автора

1. Игрок пишет `Fireball`, где память освобождается до чтения
   (`free(cell)`, затем `read(cell)`) — пример в `SPEC.md`.
2. Компилятор **пропускает** это: ошибка проявляется только в рантайме.
3. На арене каст запускается, VM доходит до чтения освобождённой ячейки.
4. Срабатывает `R003`: снаряд возникает в точке самого игрока, игрок
   получает урон и умирает.
5. Журнал показывает: номер инструкции, код ошибки, адрес ячейки, место
   освобождения. Игрок понимает причину без догадок.

## Критерии приёмки

- [ ] Лексер и парсер покрывают всю грамматику v0.1 из `SPEC.md`
- [ ] Каждая ошибка компиляции из `SPEC.md` возвращает свой код и позицию
      в исходнике (строка, колонка)
- [ ] Компилятор выдаёт байткод из набора опкодов v0.1, других опкодов нет
- [ ] VM исполняет весь набор опкодов, стек операндов и стек кадров разделены
- [ ] Лимит топлива соблюдается: при исчерпании каст обрывается с `R008`,
      частичный эффект сохраняется
- [ ] Глубина кадров ограничена, при переполнении `R001`
- [ ] Память заклинания: `alloc` / `free` / `read` / `write`, двойное
      освобождение даёт `R004`, чтение освобождённой ячейки — `R003`
- [ ] Исполнение детерминировано: один и тот же исходник на одном и том же
      состоянии арены даёт тот же результат, подтверждено golden-тестом
- [ ] Арена: игрок, один враг, снаряд, стены, попадания — всё примитивами
- [ ] Гримуар: текстовое поле, кнопка сборки, вывод диагностики
- [ ] Журнал исполнения виден в игре, а не только в stdout
- [ ] Все строки интерфейса приходят из `loc`, в ядре русского текста нет
- [ ] golden-тесты: по одному на опкод и по одному на каждый код ошибки
- [ ] `cargo fmt`, `cargo clippy -D warnings`, `cargo test` зелёные

## Порядок работы

1. `lang`: лексер + токены + golden-тесты на токенизацию
2. `lang`: парсер + AST + тесты на разбор и на ошибки `C001`–`C006`
3. `lang`: компилятор в байткод + дизассемблер (нужен для отладки и тестов)
4. `vm`: стековая машина, топливо, кадры + golden-тесты
5. `vm`: память заклинания и рантайм-ошибки `R001`–`R009`
6. `game`: арена на macroquad, сущности, снаряд, попадание
7. `game`: гримуар, журнал, связка с `loc`

Шаги 1–5 не требуют графики и тестируются из консоли. Не начинай с арены.

## Вне скоупа v0.1

Не реализовывать, даже если просто и соблазнительно:

3D · граф-редактор и дерево · параллельность и гонки данных ·
пользовательские типы · Скверна и мутации · Ларцы и протечка · Русло ·
божество-сборщик · классы и антимаг · прогрессия и грейды ·
генерация уровней · несколько врагов · сохранения · звук · ассеты ·
кластеры заклинаний и вызовы заклинания из заклинания · время сборки
против времени каста · остальные шесть образовательных тем

Всё это описано в `DESIGN.md` и ждёт своей очереди.
